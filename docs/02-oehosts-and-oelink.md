# oeHosts와 oelink

oeHosts는 도메인-IP 매핑의 이름 붙은 프로필("hosts 프로필")을 관리하고, 선택한 조합이 적용된
Chrome을 실행합니다. 이 문서는 프로필 모델, 공개 범위와 공유, 프리셋, 백업/복원, 그리고 실제
브라우저 실행을 가능하게 하는 oelink 프로토콜 핸들러를 다룹니다.

## 프로필 모델

hosts 프로필은 hosts 파일 형식의 줄(`IP hostname`, 한 줄에 하나씩)로 이루어진 이름 붙은
블록이며, 사용자가 oeHosts UI에서 직접 편집합니다. 사용자는 원하는 수만큼 프로필을 가질 수 있고
여러 개를 동시에 선택할 수 있으며, oeHosts는 선택된 프로필들을 Chrome에 넘기기 전에 하나의 규칙
집합으로 병합합니다.

병합 순서는 중요합니다. 한 프로필 안에서는 같은 호스트에 대한 첫 번째 줄이 우선합니다. 여러
프로필에 걸쳐서는, 둘 이상의 프로필에 나타나는 호스트에 대해 (선택 순서상) 먼저 오는 우선순위
높은 프로필이 이깁니다. 병합 결과는 실행 전에 UI에서 미리 볼 수 있고, 이 병합 미리보기 패널
자체를 새 프로필로 저장할 수도 있습니다. 이때 특수 플레이스홀더 `${PROXY_SVR}`(아래 참조)은
해석하지 않고 그대로 남겨 둡니다 — 그래야 저장된 프로필이 여러 머신에서도 그대로 이식됩니다.

프로필의 규칙은 `${PROXY_SVR}`을 참조할 수 있습니다. 이는 사용 시점에 요청하는 클라이언트가
보는 oeHub 자신의 주소로 해석되는 플레이스홀더로, IP를 하드코딩하지 않고 도메인을 oeProxy
리버스 프록시로 향하게 할 때 유용합니다. 포워드 프록시([03-oeproxy.md](03-oeproxy.md) 참조)
역시 연결마다 이 플레이스홀더를 해석하므로, Chrome이 `--host-resolver-rules`로 실행되든
`--proxy-server`를 통해 라우팅되든 같은 프로필 내용이 그대로 동작합니다.

hosts 페이지와 공유 페이지에 표시되는 `PROXY_SVR` 주소는 방문자가 접속한 호스트 이름(요청의
`Host` 헤더)을 DNS로 조회해 정합니다. 이 이름은 요청자가 마음대로 정할 수 있으므로, **관리자가
설정 화면의 "허용 도메인"에 등록한 이름만 조회**하고(포워드 프록시가 중계할 수 있는 도메인과 같은
목록입니다, [03-oeproxy.md](03-oeproxy.md) 참조), 그 밖의 이름과 조회 실패는 서버 자신의 주소로
대체됩니다. IP 주소로 접속하면 조회가 필요 없어 그대로 쓰입니다. 목록이 비어 있으면 어떤 이름도
조회하지 않으므로, 도메인으로 접속하는 배포에서는 그 도메인을 등록해야 `PROXY_SVR`가 도메인의
IP로 표시됩니다. `workspace` 모드에는 oeProxy가 없어 `PROXY_SVR`가 의미가 없으므로, 그 모드에서는 이 주소를
화면에 표시하지 않고 어떤 이름도 조회하지 않습니다.

## 공개 범위 (Visibility)

모든 프로필은 다음 세 가지 공개 범위 중 하나를 가집니다.

- **`private`** — 소유자에게만 보임.
- **`collabo`** — 워크스페이스 전체가 아니라, 소유자가 해당 프로필에 대해 등록해 둔 특정
  사람들과 공유됨.
- **`public`** — 워크스페이스 전역에서 보임(self-hosted 배포에서는 사실상 해당 인스턴스를
  사용하는 모든 사람에게 열려 있음). "public"의 정확한 범위는 self-hosted와 workspace 배포
  사이에서 다릅니다. 두 경우가 같다고 가정하지 말고, 그 차이는
  [04-deployment-modes.md](04-deployment-modes.md)를 참고하세요.

## 공유

프로필은 그 내용을 읽기 전용으로 보여주는 링크로 공유할 수 있습니다. workspace 배포에서는
서버가 방문자를 대신해 프로필 내용을 복호화할 수 없으므로, 이 링크는 방문자가 이미 같은
워크스페이스에 로그인되어 있을 것을 요구합니다.

이와 별개로, 프로필은 로그인이나 워크스페이스 소속과 전혀 무관하게 도달 가능한 완전한 공개
링크로도 게시할 수 있습니다. 여기에는 일반 텍스트 변형도 포함되는데, 이는 주기적인 HTTP GET만
보낼 뿐 클라이언트 측 스크립트를 전혀 실행할 수 없는 외부 hosts 파일 동기화 도구(예:
SwitchHosts)를 위한 것입니다.

인터랙티브 링크와 일반 텍스트 링크는 모두 "살아있는" 링크입니다. 소유자(공개 프로필이라면
워크스페이스 사용자 누구나)가 원본을 수정하면, 이미 발행된 링크도 그 즉시 최신 내용으로
갱신됩니다. 발행 시점의 스냅샷으로 고정되지 않습니다.

이 두 링크 유형을 뒷받침하는 암호화 방식 — 워크스페이스키와 일회성 키를 어떻게 쓰는지, 일반
텍스트 링크에서는 어떻게 평문 형태로 잠금이 풀리는지 — 는 [05-end-to-end-encryption.md](05-end-to-end-encryption.md)에
설명되어 있습니다. 이 절에서는 두 링크 유형이 어떤 용도인지만 다룹니다.

## 프리셋

프로필을 만들거나 편집할 때 "Open URL"과 "User-Agent" 필드를 빠르게 채우기 위한 두 개의 독립적인
프리셋 목록이 있습니다: 워크스페이스 관리자가 관리하고 그 워크스페이스의 모든 사용자에게 보이는
**워크스페이스** 프리셋과, 각 사용자가 스스로 관리하는 **개인** 프리셋입니다. 두 목록은 같은 빠른
채우기 드롭다운에 함께 나타나며, 개인 항목은 소유자가, 워크스페이스 항목은 그 워크스페이스의
관리자만 편집할 수 있습니다.

워크스페이스 프리셋은 워크스페이스마다 독립적입니다. 한 워크스페이스의 관리자가 등록한 프리셋은
다른 워크스페이스의 사용자에게 보이지 않고, 다른 워크스페이스의 관리자가 수정·삭제할 수도
없습니다. `self-hosted` 모드도 내부적으로 워크스페이스가 하나 만들어지므로 같은 방식으로 동작하며,
그 관리자(`adm`)가 "설정" 페이지에서 관리합니다. `workspace` 모드에서는 워크스페이스 관리자(`wsa`)가
"워크스페이스 설정" 페이지에서, 인스턴스 관리자(`adm`)는 자신이 속한 `SYSTEM` 워크스페이스의
프리셋을 "설정" 페이지에서 관리합니다.

## 내보내기, 가져오기, 백업

사용자는 자신의 hosts 프로필(그리고 기본 open URL, 시크릿 모드 선호값 같은 관련 설정)을 하나의
JSON 파일로 내보내고, 나중에 그 파일을 다시 가져올 수 있습니다. 가져올 때는 기존 프로필에
병합하거나 대체하는 방식 중 선택할 수 있습니다. 이를 통해 계정 간 프로필 이전과, oeHub 바깥에서의
임시 백업이 가능합니다.

프로필을 다시 가져오면 `collabo` 공개 범위는 `public`으로 낮춰집니다. `collabo` 프로필의 공유
목록은 특정 상위 항목을 가리키는 살아있는 참조인데, 가져오기로는 이를 복원할 수 없기 때문입니다.

## oelink

Chrome은 웹 페이지에서 직접 임의의 명령줄 플래그로 실행될 수 없습니다 — 이를 위한 브라우저
API가 없습니다. oelink은 이 공백을 메우기 위해 존재합니다: 개발자 머신마다 한 번 설치되는 작은
커스텀 프로토콜 핸들러로, `oelink://` URL 스킴을 사용합니다.

oeHosts UI가 특정 프로필이 적용된 Chrome을 실행해야 할 때 브라우저를 `oelink://` URL로
이동시키면, 운영체제가 그 URL을 설치된 oelink 핸들러에 넘깁니다. 핸들러는 인코딩된 인수
문자열을 디코드하여 Chrome을 그 인수와 함께 실행(또는 재실행)합니다.

oelink이 전달할 수 있는 플래그에는 다음이 포함됩니다.

- `--host-resolver-rules` (또는 대안으로 `--proxy-server` — 프로필이 어느 쪽을 사용할 수 있는지는
  [03-oeproxy.md](03-oeproxy.md)를 참고)
- 커스텀 user agent 문자열을 위한 `--user-agent`
- 실행된 Chrome을 자체 프로필 디렉터리로 격리하는 `--user-data-dir`
- `--incognito`
- 프로필에 설정된 임의의 추가 인수
- 개발자 도구를 자동으로 여는 옵션

지원되는 OS별로 두 개의 설치 스크립트가 있습니다.

- **Windows** — `oelink/win`. `install_win_oelink.cmd`는 사전 빌드된 `oelink.exe`를
  `%LOCALAPPDATA%\oelink`에 복사하고, `HKCU\Software\Classes\oelink` 아래에 `oelink://` URL
  스킴을 등록합니다. 로컬 CA 인증서가 함께 제공된 경우, 현재 사용자의 신뢰된 루트 저장소에도
  이를 등록합니다.
- **macOS** — `oelink/mac`. `install_mac_oelink.sh`는 AppleScript `on open location`
  핸들러(macOS가 커스텀 URL 스킴을 전달하는 메커니즘)를 감싼 작은 `.app` 번들을 빌드합니다.
  이 핸들러는 Bash 런처를 셸 아웃으로 호출하고, 런처는 인수 문자열을 base64로 디코드하여
  검증한 뒤 Chrome을 실행합니다.

`oelink/` 아래의 설치 파일들 — 사전 빌드된 Windows용 `oelink.exe` 포함 — 은 빌드 시점에 생성되지
않고 저장소에 그대로 커밋되어 있습니다. 그래서 전체 Gradle 빌드를 먼저 하지 않아도, 클론 직후
프로토콜 핸들러가 바로 동작합니다.

### URL 스킴 형식

두 플랫폼 모두 같은 스킴 형태를 씁니다: `oelink://chrome?<base64url로 인코딩된 인수 문자열>`.
인코딩된 페이로드는, 그렇지 않았다면 Chrome 명령줄에 그대로 전달되었을 인수 문자열(예:
`--host-resolver-rules="MAP example.com 127.0.0.1" https://example.com`)을 패딩을 제거한
base64url로 인코딩한 것입니다.

macOS에서는 추가로 `--oelink=<id>` 인수가 붙어, 특정 실행이 어느 Chrome 인스턴스에 속하는지
식별합니다(`--user-data-dir`이 없는 기본 프로필은 `0`, 그렇지 않으면 `--user-data-dir` 경로의
CRC32 해시). 이 덕분에 같은 프로필을 다시 실행할 때, 충돌하는 이미 실행 중인 Chrome을 감지하고
먼저 닫을지 물어볼 수 있습니다.

### 인수 검증

`oelink://` 링크는 누구나 만들어 보낼 수 있으므로(공유된 프로필, 붙여넣은 URL 등) 핸들러는 디코드한
문자열을 셸에 넘기지 않습니다. 따옴표 단위로 직접 단어를 나누고(확장·치환 없음) 각 단어를 검사하며,
하나라도 허용되지 않으면 Chrome을 전혀 실행하지 않고 안내 대화상자만 띄웁니다.

- 허용: `--플래그` 또는 `--플래그=값` 형태의 단어, 그리고 시작 URL(`http(s)://`, `about:`, `chrome://`,
  oeHosts가 만드는 지연 이동용 `data:text/html,<script>setTimeout(...)` 페이지).
- 거부: 프로그램을 실행하게 하거나(`--renderer-cmd-prefix`, `--gpu-launcher` 등), 샌드박스를
  약화시키거나(`--no-sandbox`, `--disable-web-security`), 디버깅 채널을 여는(`--remote-debugging-*`)
  플래그, 확장 로드(`--load-extension`), 트래픽 우회(`--proxy-pac-url`, `--ignore-certificate-errors*`)
  플래그, 그리고 `file:` 같은 그 밖의 URL. 거부 목록은 `chrome-launch-args.js`,
  `install_mac_oelink.sh`, `_oelink_exe.ps1`에 같은 내용으로 있으므로 함께 수정해야 합니다.

hosts 내용은 `MAP <호스트> <IP>` 규칙으로 바뀌기 전에 호스트 이름과 IP 형식만 남기고 나머지 줄은
버립니다. 사용자 에이전트·데이터 디렉터리·추가 인수 값에서는 따옴표와 제어 문자를 제거합니다.

## 모범 사례

oeHub 웹 UI 자체는 비-Chrome 브라우저(예: Edge)에서 실행하고, 실제 테스트에는 oelink이 실행하는
Chrome을 쓰세요. oelink은 프로필 전용 `--user-data-dir`로 Chrome을 실행하는데, oeHub UI도
Chrome에서 열려 있으면 두 인스턴스가 같은 user-data 디렉터리를 두고 충돌해 프로필 잠금이나
실행 충돌을 일으킬 수 있습니다. 두 브라우저를 분리해 두면, 호스트 리졸버 규칙이 실제와 똑같이
생긴 도메인을 로컬 또는 스테이징 서버로 적극적으로 리다이렉션하는 테스트 환경과, 평소의 일상적인
브라우징을 깔끔하게 나눌 수 있습니다.
