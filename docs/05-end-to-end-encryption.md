# 종단간 암호화

`workspace` 모드는 여러 워크스페이스를 하나의 인스턴스가 호스팅하는 멀티테넌트 서비스라 운영자도
호스트-IP 매핑 내용을 읽을 수 없어야 한다. 반면 `self-hosted`는 이미 신뢰하는 자신의 서버이므로
전부 평문으로 저장한다(위협 모델 비교는 [06-security-model.md](06-security-model.md) 참고).

## 적용 범위

암호화 대상은 `HOSTS_PFILE.hosts_content` 하나뿐이며, 그것도 `oe.mode=workspace`일 때만 적용된다.

- **oeProxy 가상 호스트 내용은 암호화되지 않는다.** 포워드/리버스 프록시가 라우팅 테이블을
  만들려면 평문이 필요하기 때문이다. 이 때문에 `workspace` 모드에서는 oeProxy 자체가 실행되지
  않는다([04-deployment-modes.md](04-deployment-modes.md)).
- **사용자별 설정 값**(open URL 동작, 시크릿 모드 토글 등)도 대상이 아니다. 서버가 직접 읽어
  렌더링/내보내기에 쓰며, 애초에 `visibility` 개념이 없는 값이다.

## 키 계층 구조

사용자마다 개인 RSA-OAEP(2048비트) 키 쌍을 가진다. 공개 키는 평문 저장하고, 개인 키는 항상
wrap된 채로만 저장하며 브라우저에서만 unwrap한다.

```mermaid
flowchart TD
    PW["비밀번호\n(PBKDF2-SHA256 → HKDF → AES-256-GCM KEK)"] -->|wrap| PRIV["개인 키\n(RSA-OAEP 2048)"]
    REC["비밀번호 재설정 코드\n(256비트 무작위 값)"] -->|wrap, 두 번째 방법| PRIV
    PRIV -->|unwrap| WSK["워크스페이스키\n(AES-256, 워크스페이스당 1개)"]
    PUB["공개 키\n(평문 저장)"] -.->|wrap, 멤버별| WSK
    WSK -->|wrap| DEK_PUB["콘텐츠 키(DEK)\ncollabo / public 리소스용"]
    PRIV -->|wrap| DEK_PRIV["콘텐츠 키(DEK)\nprivate 리소스용"]
    DEK_PRIV -->|암호화| CONTENT["hosts_content\n(AES-256-GCM)"]
    DEK_PUB -->|암호화| CONTENT
    WSK -->|wrap| LINKKEY["공개 링크 키"]
    LINKKEY -->|암호화| LINKCONTENT["link_content\n(수정할 때마다 갱신됨)"]
```

다이어그램이 렌더링되지 않는 환경(텍스트 뷰어 등)에서는 아래 체인으로 읽으면 된다.

- 비밀번호 → wrap → 개인 키 ← wrap ← 비밀번호 재설정 코드 (두 방법 중 하나로 unwrap 가능)
- 개인 키 → unwrap → 워크스페이스키 ← wrap(멤버별) ← 각 구성원 공개 키
- 워크스페이스키 → wrap → 콘텐츠 키(DEK, collabo/public용)
- 개인 키 → wrap → 콘텐츠 키(DEK, private용)
- 콘텐츠 키(DEK) → 암호화 → `hosts_content`
- 워크스페이스키 → wrap → 공개 링크 키 → 암호화 → `link_content`

- **개인 키 쌍(RSA-OAEP 2048)** — 사용자당 하나. 공개 키는 다른 구성원이 이 사용자를 위해 뭔가를
  감쌀 때 쓰고, 개인 키는 이 사용자의 브라우저에서만 쓰인다.
- **비밀번호 기반 KEK와 authKey** — PBKDF2-SHA256(반복 60만 회, 계정마다 무작위 16바이트 salt)으로
  비밀번호에서 마스터 값을 만들고, HKDF-SHA256으로 서로 독립인 두 값을 뽑는다. KEK(AES-256-GCM)는
  개인 키를 wrap하며 브라우저를 떠나지 않는다. authKey(32바이트)는 서버로 보내는 값으로, 서버에서
  비밀번호 대신 bcrypt로 저장·비교된다([로그인과 비밀번호](#로그인과-비밀번호) 참고). 둘 다
  결정론적으로 유도되므로 저장하지 않는다(salt만 wrap된 개인 키 레코드에 함께 저장된다).
- **비밀번호 재설정 코드** — 비밀번호와 독립적으로 생성되는 고엔트로피 값으로, 같은 개인 키를 두 번째
  방법으로 wrap한다. 가입/재발급 시 한 번만 노출되고 저장되지 않는다. 즉 개인 키는 비밀번호·복구
  코드 두 비밀 중 하나만 있어도 unwrap된다.
- **워크스페이스키(AES-KW)** — 워크스페이스당 하나. 평문 저장 없이 각 구성원의 공개 키로 개별
  wrap되어, 각자 자기 개인 키로만 자기 사본을 unwrap한다.
- **행별 콘텐츠 키(DEK, AES-256-GCM)** — 리소스(hosts 프로필)마다 무작위 생성되어 내용을 직접
  암호화한다. `private`는 소유자 개인 키로, `collabo`/`public`은 워크스페이스키로 wrap한다. 두
  공개 범위는 복호화 권한이 아니라 검색 범위에서만 다르다.

표준 봉투 암호화 패턴(AWS KMS류)으로, DEK가 콘텐츠 암호화를, KEK가 작은 키 하나의 wrap만
담당한다. 이 분리 덕분에 키 회전이 저렴하다.

서버는 wrap되거나 암호화된 자료만 저장·전달할 뿐 복호화는 하지 않는다. 모든 복호화는 브라우저의
WebCrypto API에서 일어난다.

## 로그인과 비밀번호

`workspace` 모드에서 서버는 사용자가 입력한 비밀번호를 **받지 않는다.** 로그인, 가입, 설정 마법사,
비밀번호 변경, 비밀번호 재설정 코드 재발급, 복구 후 비밀번호 재설정 모두 같은 방식이다.

1. **salt 조회**: authKey는 계정의 salt에 의존하므로 브라우저가 로그인 전에 공개 엔드포인트
   `GET /api/auth/kdf?userId=`로 salt를 받는다. 존재하지 않는 ID에는 서버 비밀로 만든 결정적 가짜
   salt를 돌려주어, 이 응답으로는 계정 존재 여부를 알 수 없다(salt는 비밀이 아니라 wrap된 개인 키
   옆에 저장되는 값이다).
2. **유도**: 브라우저가 `PBKDF2(비밀번호, salt)`에서 HKDF로 `authKey`와 `KEK`를 만든다.
3. **전송**: 기존에 비밀번호를 담던 `password` 필드에 authKey를 담아 보낸다. 서버는 이를 불투명한
   비밀값으로 보고 지금까지처럼 bcrypt로 검증한다. authKey에서는 비밀번호도 KEK도 복원되지 않는다.
4. **unwrap**: 로그인이 성공하면 브라우저가 이미 가진 KEK로 개인 키를 unwrap한다.

서버는 비밀번호로 쓰일 자리에 authKey 모양(base64url 43자)이 아닌 값이 오면 저장하지 않고
거부한다. 오래된 캐시 페이지나 손으로 만든 클라이언트가 타이핑한 비밀번호를 그대로 보내도, 서버가
개인 키를 푸는 재료를 보관하게 되지 않도록 하기 위해서다.

이 구조의 대가는 다음과 같다.

- **비밀번호 규칙은 클라이언트에서만 강제된다.** 서버가 비밀번호를 볼 수 없으므로 길이·일치 검사는
  브라우저(`auth-keys.js`)가 한다. 서버 쪽 검증은 authKey의 형식만 본다.
- **이 방식 이전에 만든 계정은 로그인할 수 없다.** KEK의 유도 방식이 바뀌어 예전 wrap을 풀 수 없다.
  개발 단계라 DB를 새로 만드는 것을 전제로 한다.
- `self-hosted` 모드는 콘텐츠를 암호화하지 않으므로 이 방식을 쓰지 않고, 비밀번호를 예전처럼
  서버로 보낸다(포워드 프록시가 같은 비밀번호로 직접 인증한다).

## 복구 흐름

비밀번호 재설정 코드를 알고 있으면, 비밀번호를 잃어도 콘텐츠 접근권을 잃지 않는다. 서버는 비밀번호 재설정 코드 자체를
결코 알지 못한 채로 요청의 정당성만 검증한다.

1. **검증값**: 브라우저가 HKDF-SHA256으로 비밀번호 재설정 코드에서 단방향 값을 유도해 그 값만 서버로
   보낸다. 서버는 이를 bcrypt로 해시해 저장하고, 두 번째 비밀번호처럼 취급한다. DB가 통째로
   유출돼도 비밀번호 재설정 코드나 개인 키는 드러나지 않는다.
2. **2단계 교환**:
   - 사용자가 ID + 검증값을 제출한다. 일치하면 서버가 wrap된 개인 키(`wrapped_private_key_recovery`,
     여전히 암호문)를 반환한다.
   - 브라우저가 (서버로 나간 적 없는) 비밀번호 재설정 코드로 개인 키를 unwrap하고, 새 비밀번호로 다시
     wrap하고, 새 비밀번호 재설정 코드를 생성해 한 번에 제출한다. 이 순간 이전 비밀번호 재설정 코드는 폐기된다.

두 요청 모두 계정 존재 여부와 무관하게 같은 일반 오류/타이밍으로 실패한다. 계정 존재 여부가
새지 않는다.

## 워크스페이스키 회전

봉투 구조 덕분에 회전은 워크스페이스키를 재생성하고 각 리소스의 DEK를 새 키로 다시 wrap하기만
하면 된다. DEK와 콘텐츠 자체는 바뀌지 않는다. 비용이 콘텐츠 크기가 아니라 리소스 개수에
비례해서, 회전이 빠르다.

- **구성원 제거 시 자동 실행.** 새 워크스페이스키를 못 받는 떠난 구성원은 이후 공유 콘텐츠를
  복호화할 수 없게 된다. 단, 떠나기 전 이미 로컬에서 본 콘텐츠까지 소급 무효화하지는 못한다.
  모델에 내재된 한계다.
- **필요 시 수동으로.** 키 유출이 의심될 때 등 "지금 회전" 동작으로 실행한다.

**실패 정책**: 구성원 제거로 인한 회전이 실패하면 제거 자체를 중단한다. 회전 없는 제거는 떠난
구성원의 접근을 못 끊기 때문이다. 같은 "지금 회전" 동작으로 재시도한다.

## 공개 링크 공유

리소스 소유자는 리소스별로 로그인 불필요한 공개 링크를 선택적으로 만들 수 있다. 워크스페이스
모델 위에 얹히는 것이며, 리소스마다 의도적으로 켜야 한다.

링크 내용은 리소스의 일반 콘텐츠 DEK와 별개인 전용 키로 암호화된다. 이 전용 키는
워크스페이스키로 wrap되어 서버에 저장되므로, 어느 구성원의 브라우저든 원본 수정 시 링크 내용을
갱신할 수 있어 링크는 항상 최신 상태다. 하지만 실제로 복호화할 수 있는 *wrap되지 않은* 키는
서버로 전송되지 않고 URL 프래그먼트(`https://.../oelink#key=...`)에만 존재한다. 프래그먼트는
HTTP 요청에 포함되지 않으므로 서버 접근 로그에도 남지 않는다.

**비-브라우저 도구용 평문 변형.** SwitchHosts 등 JS를 실행하지 못하는 도구를 위해, 같은 키를
쿼리 파라미터로 전달하는 두 번째 링크 형태도 제공한다. 이 값은 서버 접근 로그에 남을 수 있다는
트레이드오프가 있으며, 발급 시점에 사용자에게 명시적으로 안내된다.

## 리소스의 공개 범위 변경

공개 범위 변경은 콘텐츠는 그대로 둔 채 콘텐츠 키만 다시 wrap한다.

- `private`로 옮기면 → 소유자 개인 키로 다시 wrap한다.
- `public`/`collabo`로 옮기면 → 워크스페이스키로 다시 wrap한다.
- `public`을 벗어나면 → 살아있는 공개 링크는 자동 폐기된다.
