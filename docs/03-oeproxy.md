# oeProxy

oeProxy는 로컬 및 원격 가상 호스트를 위한 oeHub의 HTTPS 리버스 프록시이며, oelink 없이도 브라우저가
아닌 클라이언트와 모바일 클라이언트가 같은 라우팅에 참여할 수 있게 해주는 상시 실행 포워드
프록시이기도 합니다. 이 문서는 리버스 프록시, oeOID 헤더 태깅 메커니즘, 실시간 트래픽 모니터, 그리고
LittleProxy 의존성을 포함한 포워드 프록시를 다룹니다.

## 리버스 프록시

oeProxy는 자체 서명된 루트 인증서에서 발급된 인증서를 사용해 `443` 포트에서 여러 가상 호스트의
HTTPS를 종료합니다. 이 루트 인증서는 최초 실행 설치 마법사에서, 또는 이후 설정 페이지에서 oeHub가
직접 생성하거나 기존 것을 가져와 만들어집니다. 루트 인증서의 공개 인증서는 인증이 필요 없는
잘 알려진 엔드포인트에서도 다운로드할 수 있어서, 클라이언트 기기가 리버스 프록시와 TLS로 통신하기
전에 이를 신뢰된 인증서로 설치할 수 있습니다.

각 가상 호스트는 도메인을 로컬 또는 원격 백엔드, 그리고 그 안의 하나 이상의 위치(location)에
매핑합니다. 이 매핑은 데이터이기 때문에(hosts 프로필과 같은 방식으로 사용자별로 설정되고 편집·병합
가능하며, 설정 가능한 "로컬 서버" 주소로 해석되는 `${LOCAL_SVR}` 플레이스홀더와 병합-후-새
가상 호스트로 저장하는 동작을 포함), 같은 도메인이 어느 순간에는 개발자 자신의 머신을, 다음
순간에는 공유 스테이징 또는 프로덕션 서버를 가리킬 수 있으며, 이때 인증서를 재발급하거나 DNS를
건드릴 필요가 없습니다. 이것이 바로 팀이 "그 도메인"은 고정된 것으로 다루면서 그 뒤의 실제
백엔드는 개발자별로, 작업별로 바뀔 수 있게 해주는 요소입니다.

## oeOID

클라이언트 IP 주소는 어떤 oeHub 사용자가 특정 요청의 배후에 있는지 식별하는 신뢰할 수 없는
방법입니다 — DHCP가 주소를 재할당하고, NAT나 공유 사무실 네트워크는 여러 사용자를 하나의 눈에
보이는 IP 뒤에 둘 수 있습니다. oeOID는 이를 Chrome 확장 프로그램으로 해결하는데, oeProxy를 거치는
것으로 확인되는 모든 요청에 `X-OeHub-Oid` 헤더를 주입합니다. 이 헤더 값은 요청 사용자의 신원을
불투명하게 인코딩하고 HMAC로 서명한 것으로, 형식이 잘못되었거나 위조된 값은 IP 기반 조회로
조용히 넘어가는 대신 그 자리에서 거부됩니다. 리버스 프록시 뒤의 오리진 서비스는 이 헤더를 읽어,
어떤 네트워크 경로를 거쳤든 상관없이 요청을 특정 oeHub 사용자에게 귀속시킬 수 있습니다.

`X-OeHub-Oid` 헤더가 없을 때, oeProxy는 대신 IP 기반 식별 방식으로 대체할 수 있습니다: 사용자가
"이 IP 내가 사용" 동작을 통해 현재 브라우징 중인 IP를 명시적으로 자신의 것이라고 주장하는 시간
제한 창을 두고, 그 IP로부터의 요청은 그 주장이 만료되거나 다른 명시적 주장으로 대체될 때까지
해당 사용자에게 귀속됩니다. 이 대체 방식은 의도적으로 명시적이고 시간 제한이 있는데, 암묵적으로
"이 IP의 모든 요청을 귀속시킨다"는 방식은 그 IP를 둘 이상의 사용자가 공유하는 순간 무너지고,
식별이 암묵적인지 명시적인지에 대한 어떤 신호도 보여주지 않기 때문입니다.

## 실시간 트래픽 모니터

oeProxy는 oeProxy 페이지에서 사용자별로 접근할 수 있는 실시간 HTTP 요청 모니터를 포함합니다.
이는 (라우팅에 사용되는 것과 동일한 OID/IP 해석 방식으로) 조회 중인 사용자에게 귀속된 요청의
요청/응답 활동을 스트리밍하므로, 개발자는 다른 누군가의 트래픽을 캡처하지 않고도 리버스 프록시를
거치는 자신의 트래픽이 어떻게 보이는지 볼 수 있습니다. 이것이 모든 프록시된 트래픽에 오버헤드를
더하지 않도록, 요청/응답 본문과 헤더는 실제로 모니터 탭이 그 시점에 해당 계정을 지켜보고 있을
때만 모니터 이벤트에 복사됩니다.

## 포워드 프록시

리버스 프록시와 나란히, oeProxy는 고정 포트 `36980`에서 표준 HTTP(S) 포워드(업스트림) 프록시를
운영합니다. 이는 관리자가 켜고 끌 수 없이 항상 실행되며, 무엇이든 중계하기 전에 oeHub 계정 자체의
자격 증명으로 인증할 것을 요구합니다.

인증되면, 포워드 프록시는 해당 사용자가 현재 선택한 oeHosts 프로필에 있는 호스트로의 각 요청을
그곳에 기록된 IP로 라우팅하는데, 이는 oeHosts 자체가 병합 미리보기에 사용하는 것과 동일한 병합
규칙입니다. 이 조회는 요청마다의 데이터베이스 쿼리가 아니라, 사용자가 선택한 프로필로부터 만들어져
프로필이 편집되거나 선택이 전환될 때마다 갱신되는 사용자별 인메모리 맵에서 처리됩니다 — 그래서
인증된 중계는 부하가 걸려도 빠르게 유지됩니다. 선택된 어떤 프로필에도 없는 호스트는 일반 DNS
해석으로 대체됩니다.

oeHosts는 `--host-resolver-rules`의 대안으로 Chrome의 `--proxy-server` 플래그를 포워드
프록시로 향하게 할 수 있습니다. 고정 프록시 서버를 통해 전송되는 요청에는 Chrome이
`--host-resolver-rules`를 무시하기 때문에, 둘 중 하나를 켜면 다른 하나는 자동으로 꺼집니다.

### 도메인 화이트리스트

관리자는 포워드 프록시가 중계할 수 있는 대상을 도메인 화이트리스트로 제한할 수 있으며, 한 줄에
하나씩 설정하고 `*.` 접두사는 해당 도메인과 그 모든 하위 도메인에 매칭됩니다. 화이트리스트가
비어 있으면(기본값) 중계는 제한되지 않습니다. 차단된 목적지는 리버스 프록시 자체의 오류 페이지와
일치하는 브랜드가 적용된 403 오류 페이지를 받습니다. 차단된 HTTPS 목적지의 경우, CONNECT
터널이 그냥 실패하는 대신 포트 `36981`의 전용 루프백 전용 TLS 응답기로 리다이렉션되며, 이
응답기는 요청된 호스트에 대해 인증서 기관이 발급한 인증서로 TLS 핸드셰이크를 완료하고 같은
브랜드 페이지를 제공합니다 — 그래서 차단된 HTTPS 요청도 차단된 HTTP 요청과 동일하게 렌더링됩니다.

### 모바일 및 브라우저가 아닌 클라이언트

포워드 프록시는 표준 HTTP(S) 프록시이기 때문에, oelink을 통한 Chrome뿐 아니라 프록시 설정을
지원하는 어떤 클라이언트든 사용할 수 있습니다. 모바일 기기는 자신의 Wi-Fi 프록시 설정을 이
포워드 프록시로 지정하는 방식으로 트래픽을 리다이렉션할 수 있으며, 모바일에는
oelink/host-resolver-rules에 해당하는 것이 필요 없습니다. 다만 두 주요 모바일 플랫폼은 여기서
차이가 있습니다: iOS의 Wi-Fi 프록시 설정은 인증을 지원하므로, 인증된 프록시 구성이 iOS에서
브라우저 트래픽과 앱 트래픽을 모두 커버합니다. Android의 Wi-Fi 프록시 설정은 인증 지원이 전혀
없어서, (프록시가 자격 증명을 요구할 때 사용자에게 직접 물어볼 수 있는) 브라우저만 실제로 이를
사용할 수 있고, Android의 다른 앱 트래픽은 프록시를 거치지 않습니다.

## LittleProxy 의존성

포워드 프록시는 [LittleProxy](https://github.com/LittleProxy/LittleProxy) 라이브러리 위에
구축되어 있습니다. LittleProxy에는 원시(비-MITM) HTTPS `CONNECT` 터널의 서버 측 연결을 추적하는
방식에 영향을 주는 알려진 내부 버그가 있는데, oeProxy는 특정 기능을 위해 이에 의존합니다: 포워드
프록시 요청이 oeProxy 자신의 리버스 프록시로 되돌아 들어오는(self-loop) 상황을 인식하여, 이를
인증된 포워드 프록시 사용자에게 자동으로 귀속시키는 기능입니다. oeHub는 문서화된, 격리된
리플렉션 기반 기법(`tricatch.oe.proxy.util.LittleProxyInternals`)으로 이 버그를 우회하여 필요한
살아있는 연결 상태에 접근합니다.

이 우회책은 의도적으로 안전하게 실패하도록 만들어졌습니다: 미래의 LittleProxy 버전이 의존하는
내부 필드의 이름을 바꾸거나 제거하면, 리플렉션 호출은 예외를 던지는 대신 그냥 null을 반환하고
경고를 한 번만 기록합니다. 그런 경우 self-loop 귀속은 더 이상 동작하지 않지만, 나머지는 모두
계속 동작합니다 — `X-OeHub-Oid` 헤더와 "이 IP 내가 사용" 주장 메커니즘은 귀속 경로로서 완전히
기능을 유지합니다. 정확한 메커니즘과 필드 이름은 해당 클래스 자체의 문서를 참고하세요. 이 문서에서
의도적으로 중복 설명하지 않습니다.

## workspace 모드에서 적용되지 않는 것

가상 호스트와 포워드 프록시 설정 내용은, hosts 프로필 내용과 달리, workspace 배포에서도 결코
종단간 암호화되지 않습니다. 더 근본적으로, oeProxy 전체 — 리버스 프록시, oeOID, 트래픽 모니터,
포워드 프록시 — 는 workspace 모드에서 아예 사용할 수 없습니다. 그 어떤 서버도 시작되지 않고 어떤
라우트도 등록되지 않습니다. 이는 UI 수준의 토글이 아니라 의도적이고 구조적인 배제입니다. workspace
모드가 무엇인지, 그리고 왜 oeProxy가 여기서 제외되는지는 [04-deployment-modes.md](04-deployment-modes.md)를,
oeProxy의 설정이 왜 hosts 프로필에 사용되는 암호화 모델의 범위 밖에 있는지는
[05-end-to-end-encryption.md](05-end-to-end-encryption.md)를 참고하세요.
